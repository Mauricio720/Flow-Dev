# ADR-001: Continue the existing change through planning in Issues

## Status

Accepted

## Date

2026-10-05

## Context

The existing Issues workspace retains intentions, conversations, draft revisions, and a confirmed GitHub publication. Its current completion boundary is publication. The requested feature extends that boundary through a human-approved development route without implementing downstream development stages.

## Decision

Use the existing Issues entry and selected intention as the continuing work item. Preserve the task's identity, project, author, repository, conversation, and published Issue. Add an explicitly requested Dev Control analysis, a durable PlanningDecision, human route review, and a distinct planning step in the lifecycle.

The approved publication snapshot is the Issue content being planned. Existing published tasks are eligible under the same rules as newly published tasks. A live GitHub edit does not silently replace that snapshot. Keep Issue and PlanningDecision distinguishable as artifacts of the same change; renaming existing entities is not a product requirement.

Only the author can start or retry planning, change the route, and approve it. Authorized project members and administrators can read, subject to their own repository access. Existing administrative status does not confer authorship override.

## Alternatives Considered

### Alternative 1: Introduce a separate planning workspace

- **Description**: Start a new planning item from another navigation entry.
- **Pros**: Planning has an independent entry point.
- **Cons**: Splits one change across places and weakens continuity with its evidence and publication.
- **Why rejected**: The source explicitly keeps Issues as the entry point and the intention as the continuing change.

### Alternative 2: Treat the GitHub Issue as the entire workflow container

- **Description**: Place planning and later decisions primarily in GitHub content or comments.
- **Pros**: Centralizes visible content on GitHub.
- **Cons**: Adds external writes, blurs artifacts and lifecycle, and conflicts with the requested Flow Dev Human View.
- **Why rejected**: Planning belongs to Flow Dev; the source requests typed, related outputs and does not require publishing planning to GitHub.

## Consequences

### Positive

- Developers continue the same change without recreating context or publishing another Issue.
- Shared readers retain the existing access and ownership expectations.
- Later artifacts can attach to the same change without making the Issue contain every stage.

### Negative

- The existing publication-as-completion language and status presentation must evolve.
- Historical published tasks need a coherent awaiting-planning experience.

### Risks

- The existing Dev Control gateway only proves Issue Author integration. The TechSpec must establish the planning capability and cannot reuse a draft-generation response as a PlanningDecision.
- The old task-creation PRD says publication ends the journey. This ADR supersedes that boundary only; published content remains immutable in Flow Dev.

## Implementation Notes

Select transport, state representation, persistence, and integration details in the TechSpec. Preserve the current authorization and durable-operation guarantees. Do not require new navigation, all proposed future tabs, or an entity rename.
