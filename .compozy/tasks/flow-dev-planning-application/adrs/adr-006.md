# ADR-006: Define a dedicated snapshot-only Dev Control planning protocol

## Status

Accepted

## Date

2026-10-05

## Context

The existing Dev Control gateway calls `/flow-dev/issue-author/v1` and accepts draft or clarification output. It does not establish a planning endpoint. On 2026-10-05 the user selected option A: define a new planning contract in this TechSpec and record its implementation in Dev Control as a delivery dependency.

## Decision

Specify `POST /flow-dev/planning/v1` as a new, authenticated, side-effect-free analysis operation. The Flow Dev worker sends the retained approved publication snapshot, stable repository/Issue association, operation/execution identifiers, and a canonical input hash. The provider returns a bounded, validated recommendation with complexity, summary, reasons, and uncertainties. Flow Dev creates the decision identity, default selection, provenance, review state, and any subsequent approval.

Dev Control must deduplicate analysis by logical operation ID and input hash and return the same result on replay, echoing the current execution correlation. The protocol is synchronous from worker to provider and asynchronous from browser to Flow Dev. Flow Dev remains the durable queue and authority for saved state. No callback, browser streaming, provider session, GitHub token, context capability, or repository lookup is required in v1. The publication snapshot is the recorded planning basis. The provider must not execute routes, publish comments, modify Issues, or invent source/tool activity.

The Dev Control service owner must implement and deploy this new protocol; that external deliverable is not present or verified in this repository. Flow Dev's implementation owner builds its gateway and contract harness. Release requires a real staging contract check against Dev Control. Mocks cannot fulfill that gate.

## Alternatives Considered

### Alternative 1: Reuse Issue Author output as planning

- **Description**: Add a prompt or parse a draft into a route recommendation.
- **Pros**: Uses the known endpoint.
- **Cons**: Neither the response schema nor recovery semantics establish planning capability.
- **Why rejected**: Would substitute an unverified integration for the real capability required by the PRD.

### Alternative 2: Require provider jobs, callbacks, and repository tools

- **Description**: Add an external job lifecycle and live repository exploration to every analysis.
- **Pros**: Supports longer analyses and richer new evidence.
- **Cons**: Adds callback authentication, duplicate event handling, and context authorization beyond the retained-snapshot requirement.
- **Why rejected**: Snapshot analysis and the existing worker satisfy this scope. A later version may add actual recorded evidence without changing the current artifact's basis.

## Consequences

### Positive

- A concrete contract separates external analysis from local human decisions.
- Recovery can safely replay analysis without risking external writes.
- Credentials and unrelated conversation content do not enter the provider request.

### Negative

- Shipping depends on coordinated changes in another service.
- Analysis cannot claim fresh repository inspection; uncertainties must express missing context.

### Risks

- The external implementation could lack deduplication or violate the deadline; staging must exercise replay, correlation, output validation, and limits before release.
- Provider text can contain hostile content; validate structure and render escaped text.

## Implementation Notes

The TechSpec defines all request fields, response fields, hashes, limits, errors, retry behavior, and server-only configuration. The endpoint path is a proposed required contract, not a claim about a deployed route. User clarification resolved the external ownership boundary; remaining numerical budgets are explicit engineering defaults for this delivery.
