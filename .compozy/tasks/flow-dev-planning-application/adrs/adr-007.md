# ADR-007: Version route review and render typed artifacts in the existing workspace

## Status

Accepted

## Date

2026-10-05

## Context

ADR-003 makes approval explicit and final. Concurrent tabs and lost responses can otherwise approve a route different from the one reviewed. The existing UI scopes requests by task, but published tasks stop polling and its reducer does not reject a lower task version.

## Decision

Persist the original assessment separately from the selected route and its selection version. Route changes and approval require the task ID, decision ID, expected task version, and expected decision version. Approval also includes the reviewed selected route. Serialize commands on the task row and check the exact saved decision under the same transaction. Replays use scoped command receipts; repeat approval of the same approved selection returns its original identity and timestamp.

Never optimistically show saved selection or approved status. While a route is dirty, saving, or uncertain, block approval locally and retrieve authoritative state before permitting it. Ignore older workspace versions and responses for another selected task. Refresh planning state while the workspace is visible, including after approval so access revocation is detected on subsequent protected reads.

Render a named PlanningDecision Human View and a separate published Issue detail within the existing Issue Composer. Keep the lifecycle and current human action visible independently of paginated conversation. Use existing typography, tokens, accessibility primitives, and timeline vocabulary. The three route options are descriptions of the next activity, not future running stages.

## Alternatives Considered

### Alternative 1: Last-write-wins approval and optimistic UI

- **Description**: Save the most recently received route or approval without checking the reviewed version.
- **Pros**: Fewer conflict states.
- **Cons**: A stale tab can silently change or approve another selection; a failed request can look successful.
- **Why rejected**: Violates the PRD's exact-review and saved-state guarantees.

### Alternative 2: Introduce four mandatory tabs and a global client cache

- **Description**: Move the workspace into a new Flow/Conversation/Artifacts/Sources navigation system.
- **Pros**: Strong top-level separation for many future artifacts.
- **Cons**: Requires new navigation and state ownership before those artifacts exist.
- **Why rejected**: Named sections and accessible details meet current separation requirements within the existing feature.

## Consequences

### Positive

- Approval identifies one stable, reviewed route and person.
- Readers and authors converge on the same saved result.
- Structured artifacts remain understandable without loading the full conversation.

### Negative

- Stale authors must refresh and review again.
- Polling has a bounded ongoing read cost while a published workspace is visible.

### Risks

- Cached data can survive an access error; clear protected content on authentication/authorization failures, while retaining the last confirmed view only for transient failures.
- Current design guidance calls the draft the only artifact container; update that guidance during implementation to accommodate planning explicitly.

## Implementation Notes

Selection version increments only when the saved route changes. Approval freezes that version and increments the task version. Returning to the recommendation restores selection source `AI`, without changing human approval attribution. No uncertainty acknowledgement or downstream dispatch is introduced.
