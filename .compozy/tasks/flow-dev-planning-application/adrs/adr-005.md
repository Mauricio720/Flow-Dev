# ADR-005: Extend published tasks with durable local planning

## Status

Accepted

## Date

2026-10-05

## Context

The repository has PostgreSQL/Drizzle task records, immutable confirmed publication snapshots, idempotent command receipts, and a separate `tasks:worker` process. Publication is currently the terminal `tasks.status`. Generation claims already use leases, fencing, and `FOR UPDATE SKIP LOCKED`. Replacing publication status would affect existing authoring guards and obscure a retained fact.

## Decision

Keep `tasks.status = published` throughout planning. Add a nullable planning status, a typed `task_planning_decisions` table, and the `plan` operation kind to the existing durable queue. Derive awaiting planning from a published task with no planning status; do not backfill fabricated attempts or decisions. Bind planning operations and decisions to the confirmed publication attempt, which owns the original Issue identity and snapshot.

Use the existing task version for coherent workspace reads and commands. Keep one decision per task and one active operation using database constraints. A planning worker participates in the existing two-slot worker pool with fair scheduling across generation, publication, and planning. Reuse lease/fence mechanics, but keep planning settlement separate from generation settlement, which otherwise restores authoring states.

Keep contracts in `packages/api/src/application/`, controllers in `controllers/`, persistence and HTTP implementations in `infra/`, and planning UI inside the existing Issue Composer feature. Do not introduce a new package, message broker, generic workflow engine, or generic artifact store.

## Alternatives Considered

### Alternative 1: Replace the task status with planning lifecycle values

- **Description**: Add planning states directly to the authoring/publication status union.
- **Pros**: One status field for all phases.
- **Cons**: Every existing published-state guard must change; publication ceases to be directly represented.
- **Why rejected**: An additive planning status preserves existing publication and authoring invariants with less migration risk.

### Alternative 2: Add a separate work-item subsystem and queue

- **Description**: Migrate tasks into generic work items and introduce a separate orchestrator.
- **Pros**: Supports arbitrary future stages.
- **Cons**: Requires identity migration and new infrastructure without a requirement in this delivery.
- **Why rejected**: Existing tasks, operations, and publication attempts already provide the required ownership and durability boundaries.

## Consequences

### Positive

- Historical publications become eligible without writes on read.
- Existing publication constraints and snapshots remain authoritative.
- Database transactions enforce a single current result across worker restarts.

### Negative

- Consumers must distinguish publication status from planning status.
- Existing published-item polling must change to observe planning.

### Risks

- Generation settlement must never claim or settle `plan` operations; test kind isolation.
- A mixed workspace read could pair a newer decision with an older task version; use a consistent database snapshot.
- A slow planning request can occupy a worker slot; bound processing and alternate eligible operation kinds.

## Implementation Notes

See the TechSpec for schema constraints, transaction ordering, worker deadlines, release order, and exact file ownership. Update the hard-coded migration list in `packages/api/test/database.ts` with the generated migration. No source code is changed by this ADR.
