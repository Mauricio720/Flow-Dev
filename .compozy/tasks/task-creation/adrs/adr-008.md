# ADR-008: Dispatch publication once and preserve unresolved uncertainty

## Status

Accepted

## Date

2026-10-01

## Context

GitHub Issue creation is an external write. The documented REST creation endpoint has no request-level idempotency key contract. A database transaction cannot atomically include GitHub creation. The PRD explicitly accepts a blocked uncertain attempt when automatic reconciliation cannot establish its outcome, and requires publication of exactly the reviewed canonical content.

## Decision

Persist the approved revision, repository identity, publisher and rendered title/body before dispatch. Atomically mark an attempt dispatching exactly once. Disable automatic HTTP/SDK/proxy retries of Issue creation. A fully received verified creation receipt establishes success; a definitive GitHub rejection establishes noncreation. Any transport ambiguity, malformed success, worker loss after the dispatch fence, or response-storage gap enters publication_uncertain.

Recovery consumes the original attempt's durable or late authenticated response and validates any known Issue identity against the bound repository. Without an attributable receipt, repository listings may suggest candidates for verification guidance, but neither a title/body match nor an empty search proves the attempt's outcome. Keep creation blocked indefinitely when evidence is inconclusive. Never clear uncertainty merely because a timeout elapsed or the author returned from OAuth.

Do not append hidden attempt markers, diagnostic comments or metadata to the Issue body. Do not claim exactly-once remote delivery; provide at-most-one dispatch per possibly successful attempt and evidence-based terminal states. A new explicitly approved attempt is allowed only after established noncreation.

## Alternatives Considered

### Alternative 1: Retry after a timeout or missing search result

- **Description**: Assume failure when no Issue is immediately visible.
- **Pros**: Simple recovery interaction.
- **Cons**: GitHub may have created the Issue before the response was lost; search can be incomplete or delayed.
- **Why rejected**: Can create duplicates and violates PRD publication recovery.

### Alternative 2: Append a correlation marker to the Issue

- **Description**: Add a unique attempt ID in a hidden HTML comment or extra content field.
- **Pros**: Improves attribution during repository scans.
- **Cons**: Adds workflow diagnostics beyond the accepted canonical content and preview.
- **Why rejected**: The accepted content-only publication and PRD body rules determine this boundary.

## Consequences

### Positive

- Refresh, retries, restarts and multiple workers cannot blindly create another Issue.
- Publication remains faithful to the displayed title/body.

### Negative

- A response lost before durable storage can leave an attempt blocked even if the Issue exists.
- Human inspection may be needed; the feature does not offer a force-retry escape hatch.

### Risks

- A unique-looking Issue is not conclusive attribution; retain the uncertain state unless the original receipt establishes the link.
- A crash between fencing and HTTP may block a never-sent attempt. This conservative failure favors the PRD's no-duplicate rule.
- Permissions can change after preflight; record confirmed external results even when access is subsequently revoked, but protect all reads.

## Implementation Notes

Return "Verificando publicação" with destination guidance. Preserve all receipts, attempt state and review snapshots. Persist a late definitive rejection for the same attempt before enabling a new approval. Follow redirects only after resolving the stable repository identity; no create retry on 301/307/308.
