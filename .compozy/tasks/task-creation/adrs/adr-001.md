# ADR-001: Create one reviewed GitHub Issue from each task

## Status

Accepted

## Date

2026-10-01

## Context

The user requested the complete task-creation journey through GitHub publication. Flow Dev's product principles require explicit developer approval. The sibling Dev_Control application already provides Issue Author, which returns either a clarification question or an Issue draft and does not publish. The current workspace simulates generation and publication.

## Decision

Each task belongs to one Flow Dev project and targets that project's stable GitHub repository. Issue Author generates and refines the content. The author reviews the current draft and explicitly selects “Criar Issue”; Flow Dev publishes that exact revision using the author's authorized GitHub identity and saves the returned Issue identity and URL. One task produces one Issue. Generation, dictation, and conversational instructions never constitute publication approval.

Use the agent's canonical content: title, context, objective, constraints, relevant context with sources, product considerations, and references. Support manual edits and conversational refinements. Do not add a separate metadata-selection step or generate additional acceptance criteria. The user explicitly selected content-only publication.

## Alternatives Considered

### Alternative 1: Agent publishes automatically

- **Description**: Create the GitHub Issue as soon as a draft is generated.
- **Pros**: Fewer user actions.
- **Cons**: Unreviewed content creates an external artifact.
- **Why rejected**: Conflicts with the existing explicit-approval product rule.

### Alternative 2: Expand the draft with labels, assignees, and additional criteria

- **Description**: Preserve the prototype's extra fields and add GitHub metadata controls.
- **Pros**: More triage options before publication.
- **Cons**: Changes the existing agent's responsibility and introduces metadata permissions.
- **Why rejected**: The user selected only the agent's content, with manual and conversational editing.

## Consequences

### Positive

- The author controls the content and publication destination.
- Flow Dev reuses the existing authoring behavior and preserves its evidence boundaries.

### Negative

- Publication remains an explicit action after generation.
- The prototype's draft model must be aligned with the actual agent output.

### Risks

- A lost GitHub response can leave an uncertain outcome; reconcile before allowing another creation attempt.
- Approval of an outdated revision could publish unexpected content; bind approval to the reviewed revision and repository.

## Implementation Notes

The TechSpec must resolve authenticated integration with Dev_Control, draft rendering, revision handling, GitHub authorization, and publication recovery. This decision does not prescribe transport or storage.
