# ADR-004: Ground generation in the selected project's GitHub repository

## Status

Accepted

## Date

2026-10-01

## Context

Flow Dev's project PRD establishes GitHub as the sole source of project code. The existing Issue Author searches files inside Dev_Control and uses a globally configured token for GitHub Issue tools. Its route accepts conversation messages without a project binding and returns a final structured result without a user-facing tool activity trace. Those defaults do not establish a safe connection to the selected Flow Dev project.

## Decision

Every generation request uses the task's selected project repository and the current author's authorized access. Read code from that repository and confine Issue searches to it. Never substitute Dev_Control's own code, another selected project, or access granted only to a service identity.

Preserve the agent's selective evidence behavior: consult relevant project code when helpful; consult GitHub Issues when the user's request refers to existing work, duplicates, or repository history. Clarify only when the requested task cannot be identified. Show real activity and exact returned sources; do not invent tool calls, timings, paths, or Issue numbers to fill the existing interface. Missing optional evidence must be visible and must not prevent an otherwise identifiable request from producing a faithful draft.

## Alternatives Considered

### Alternative 1: Call the existing route with messages only

- **Description**: Reuse its current local and global context unchanged.
- **Pros**: Minimal integration work.
- **Cons**: Can ground a task in the wrong codebase and bypass personal repository access boundaries.
- **Why rejected**: Conflicts with the project's GitHub-only source and user permission rules.

### Alternative 2: Always search every context source

- **Description**: Run the same fixed sequence of code and Issue tools for every input.
- **Pros**: Predictable visual activity.
- **Cons**: Adds irrelevant context and contradicts the existing agent's selective tool use.
- **Why rejected**: The requested feature integrates the existing agent rather than changing its authoring responsibility.

## Consequences

### Positive

- Evidence belongs to the task's actual repository.
- Users can distinguish retrieved context, absent context, and failed retrieval.

### Negative

- Dev_Control needs an integration boundary beyond its current local configuration.
- Some requests produce no tool activity because no lookup is necessary.

### Risks

- Repository files and Issue text can contain instructions; treat them as evidence, not authority to change scope, access, or publication rules.
- Old evidence may become unavailable; retain accurate provenance without claiming it describes current repository state.

## Implementation Notes

The TechSpec must resolve repository binding, per-user access enforcement, source validation, and exposure of actual activity. It may use a repository-derived working copy, but local folders are not a user-selectable source of truth.
