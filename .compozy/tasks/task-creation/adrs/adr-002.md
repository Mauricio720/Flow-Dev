# ADR-002: Share task history while reserving changes to the author

## Status

Accepted

## Date

2026-10-01

## Context

The workspace currently holds demonstration sessions in browser memory. The user chose shared visibility within the project, with editing and publication restricted to the task's author. Existing project membership and personal GitHub access rules continue to apply.

## Decision

Persist tasks, conversations, confirmed inputs, draft revisions, and publication results. Authorized project members may view task history. Only the original author may send messages, change a draft, request regeneration, or publish. Administrators inherit project visibility but receive no override of authorship. A task's project and author remain fixed.

Resumption restores confirmed work after navigation, refresh, sign-in, and service restart. Browser-local text that has never been saved must not be presented as durable. Shared viewing does not expose private repository content to members lacking their own GitHub access.

## Alternatives Considered

### Alternative 1: Private author-only history

- **Description**: Hide unpublished tasks from other members.
- **Pros**: Simple visibility boundary.
- **Cons**: Prevents the requested team visibility.
- **Why rejected**: The user selected shared project visibility.

### Alternative 2: Collaborative editing and publication

- **Description**: Let any authorized member change or publish a task.
- **Pros**: Enables handoff between members.
- **Cons**: Adds shared editing conflicts and changes ownership of approval.
- **Why rejected**: The user explicitly reserved editing and publication to the author.

## Consequences

### Positive

- Members can consult the task's intent, evidence, and outcome.
- Authorship provides an unambiguous mutation boundary.

### Negative

- Other members cannot finish a task for an unavailable author.
- Persisted work requires honest save and recovery feedback.

### Risks

- Shared history can expose private code; enforce both project membership and the viewer's GitHub access.
- Multiple tabs can edit stale versions; require conflict recovery without silently overwriting newer work.

## Implementation Notes

The TechSpec owns persistence, ordering, conflict handling, and pagination. Preserve existing authentication and project access rules.
