# ADR-003: Provide editable dictation on desktop and mobile

## Status

Accepted

## Date

2026-10-01

## Context

The user requested microphone input and chose editable dictation followed by manual submission. They also chose support on computers and phones in the main browsers. Native browser speech recognition has uneven availability and can send audio to a remote recognition service.

## Decision

Offer an explicit microphone control in the task's message input. Speech becomes editable text; the author reviews it and selects Send. Apply the same behavior to initial intent, clarification replies, and refinement requests. Preserve typed text when dictating, and never send or publish automatically because speech ended.

Require working voice input in supported current desktop Chrome, Edge, Firefox, and Safari, Android Chrome, and iOS Safari. The speech mechanism must meet this coverage rather than depend exclusively on a limited native speech-recognition API. Other mobile browsers may use the same capability where supported; they are not a separate compatibility guarantee.

Use pt-BR as the default dictation language. Request microphone permission only following the user's action. Make recording and processing states visible, offer stop and cancel, and stop microphone capture on navigation, task switching, sign-out, and permission loss. Keep typing available when microphone permission, device availability, or transcription fails. Retain submitted text as conversation content; do not retain raw audio as a task attachment or put it in GitHub. Disclose any remote audio processing before the first capture.

## Alternatives Considered

### Alternative 1: Record and submit audio messages

- **Description**: Treat recordings as messages and transcribe them after capture.
- **Pros**: Familiar voice-message pattern.
- **Cons**: Changes the chosen text-input interaction and invites audio history.
- **Why rejected**: The user chose dictation into an editable input.

### Alternative 2: Full voice conversation

- **Description**: Submit speech directly and speak the agent's responses.
- **Pros**: Enables a hands-free conversation.
- **Cons**: Adds voice responses and reduces the text-review checkpoint.
- **Why rejected**: The user chose editable dictation with manual Send.

### Alternative 3: Chrome desktop only

- **Description**: Limit the feature to one browser and device class.
- **Pros**: Smaller compatibility surface.
- **Cons**: Leaves requested desktop and mobile contexts without voice input.
- **Why rejected**: The user selected computers and phones in the main browsers.

## Consequences

### Positive

- Authors can correct names, code terms, and transcription errors before sending.
- Voice and typing share the same task-authoring workflow.

### Negative

- Compatibility requires verification across desktop and mobile environments.
- Dictation still requires manual text submission.

### Risks

- Permission denial, noise, or service failure can interrupt dictation; preserve pre-existing text and provide retry guidance.
- Late transcription results could enter another task; bind results to the originating input and discard canceled results.

## Implementation Notes

The TechSpec must select a transcription mechanism and define processing limits and provider retention. The browser matrix above is a product requirement, not a library choice.
