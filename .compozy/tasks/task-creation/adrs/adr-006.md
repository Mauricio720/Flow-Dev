# ADR-006: Persist task revisions and execute durable operations in PostgreSQL

## Status

Accepted

## Date

2026-10-01

## Context

Tasks currently exist in browser memory and use scripted generation/publication. PostgreSQL, Drizzle, authenticated tRPC and personal repository authorization already exist. ADR-002 and the PRD require confirmed history across restarts, author-only mutations, ordered operations and safe repeat submission.

## Decision

Extend packages/api with task, message, immutable draft revision, operation, evidence and publication attempt records. Commit message acceptance and its generation operation together. Use request keys with payload hashes, task versions, an active-operation constraint and short transactions. Keep project, author and stable GitHub repository identity immutable.

Run an internal `tasks:worker` CLI from packages/api on the existing VPS. Claim queued work with PostgreSQL row locks, leases and fencing; perform external HTTP outside transactions. Retry interrupted generation under the same logical operation, but never automatically repeat a publication dispatch. A potentially dispatched publication remains uncertain until conclusive evidence establishes the outcome. Persist published snapshots and provider receipts independently of browser lifetime.

Preserve full accepted conversation within an explicit generation input budget. Reject over-budget new authoring requests before acceptance and retain their editable input. Do not silently drop old messages or introduce a summarization service. Keep history/revision pagination independent of the generation budget and impose no task-count quota.

## Alternatives Considered

### Alternative 1: Execute only inside browser-triggered HTTP requests

- **Description**: Keep long generation/publication calls attached to Next.js request lifetimes.
- **Pros**: No worker process.
- **Cons**: Restarts and request interruption leave no reliable execution owner; automatic retries can duplicate external creation.
- **Why rejected**: Cannot satisfy durable operation recovery safely.

### Alternative 2: Redis queue and separate task package

- **Description**: Add a broker and dedicated workflow package.
- **Pros**: Mature queue tooling and independent scaling.
- **Cons**: Another service and deployment boundary without current volume evidence.
- **Why rejected**: Existing PostgreSQL and VPS support the required durable queue without additional infrastructure.

### Alternative 3: Automatic history summarization

- **Description**: Replace older conversation with a model-generated summary.
- **Pros**: Longer conversational sessions within a smaller model budget.
- **Cons**: Adds another generation operation and can lose explicit requirements or author decisions.
- **Why rejected**: An explicit recoverable input-capacity error is simpler and preserves confirmed context exactly.

## Consequences

### Positive

- Database invariants settle double submissions and multiple tabs.
- Durable history is independent of frontend timers and process memory.

### Negative

- Deployments must supervise an additional worker process.
- Very long authoring conversations receive an explicit capacity limit even though saved history remains accessible.

### Risks

- Expired publication leases cannot prove noncreation; recovery never dispatches again.
- API and worker may rotate one user's OAuth token concurrently; serialize refresh through PostgreSQL and revalidate GitHub identity.
- Fencing must prevent a superseded generation result from replacing current work.

## Implementation Notes

Follow existing application contracts / infra implementations / class controller boundaries. Add migrations to packages/api/drizzle; do not edit or reset unrelated pending migrations. The worker has no public trigger endpoint and no GitHub token in persisted job payloads.
