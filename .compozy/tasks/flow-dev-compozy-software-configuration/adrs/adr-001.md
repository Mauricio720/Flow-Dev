# ADR-001: Configure Compozy from a global Software area

## Status

Accepted

## Date

2026-10-06

## Context

The existing Spec workflow expects operator-provided runtime settings. Flow Dev currently has global administrator access management and project-specific settings, but no Software area. Runtime readiness and provider connections belong to the deployed environment; asking each task author to manage them would duplicate sensitive setup and make readiness unclear.

## Decision

Add a global Software area for Flow Dev administrators to manage Compozy application settings, connect supported provider accounts, and inspect a truthful readiness checklist. Account connection and reconnection happen through the application. Host prerequisites that require machine administration are diagnosed and explained there, not silently installed or bypassed by the web application. A task author chooses from ready connections in the task workspace.

## Alternatives Considered

### Alternative 1: Project settings own Compozy setup

- **Description**: Repeat runtime and provider configuration in every project.
- **Pros**: Keeps setup near each project's work.
- **Cons**: Duplicates environment-level settings and increases credential exposure and drift.
- **Why rejected**: The runtime is shared infrastructure, while usage choices belong to tasks.

### Alternative 2: Web menu provisions every host dependency

- **Description**: Let the browser install or change the machine's container runtime, image, and network policy.
- **Pros**: One apparent setup surface.
- **Cons**: Requires host administration authority and makes safety failures easy to hide behind a successful form.
- **Why rejected**: The user chose application-level setup with diagnosis and instructions for host prerequisites.

## Consequences

### Positive

- Administrators have one place to connect accounts and see what is ready.
- Task authors do not need host access or credentials to choose an approved execution option.

### Negative

- Some readiness failures still require an operator to act on the host.

### Risks

- A superficial health indicator could invite an unsafe start; readiness must distinguish application settings, provider authentication, and host isolation.

## Implementation Notes

The TechSpec must define safe credential handling, host diagnostics, and how settings become effective without exposing secrets to task pages.
