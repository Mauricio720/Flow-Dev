# ADR-006: Follow the CompozyOS unified spec and Loop lifecycle

## Status

Accepted

## Date

2026-10-06

## Context

The earlier Flow Dev Spec design uses separate PRD, Tech Spec, and Tasks stages. CompozyOS 0.3's `spec-cycle` extension instead uses `cy-create-spec` to author one `_spec.md` with Product and Technical parts and companion contracts, then `cy-create-tasks`. It bundles `implement-tasks` and `review-and-fix` Loops, but no Spec-authoring Loop. The user explicitly chose to follow how CompozyOS works and to determine the flow.

## Decision

For new Flow Dev spec-driven executions **after this feature is implemented**, use the CompozyOS unified `_spec.md` and applicable companion contracts as the canonical spec package. Let the task author choose which eligible skill and Loop actions to run, including optional implementation and review Loops, using live CompozyOS definitions and inputs. Each action requires an explicit start and its own runtime confirmation. Existing split-stage attempts and approved PRD/Tech Spec packages remain readable and are not silently converted. This decision supersedes ADR-002's task-wide, split-stage binding and the related assumptions of the earlier Spec PRD for new flows. This feature's own development artifacts remain `_prd.md`, `_techspec.md`, `_tests.md`, and the task files expected by the locally installed Compozy 0.2 workflow.

## Alternatives Considered

### Keep separate PRD and Tech Spec as the future contract

- **Pros**: Fewer changes to the existing Flow Dev UI and worker.
- **Cons**: Diverges from the current `cy-create-spec` and `cy-create-tasks` contract; needs a permanent translation layer.
- **Why rejected**: The user chose the CompozyOS workflow as the source of truth.

### Treat spec creation as a bundled Loop

- **Pros**: One execution abstraction for every step.
- **Cons**: The pinned runtime ships no such Loop; claiming one exists would fabricate a contract.
- **Why rejected**: Spec creation is a skill-driven managed session in the inspected release.

## Consequences

### Positive

- New Flow Dev artifacts and task decomposition follow the upstream CompozyOS format.
- The author can choose which supported work to run and inspect actual Loop outcomes.

### Negative

- Legacy and new artifact views coexist until a separately designed migration is justified.
- Flow Dev needs separate adapters for skill-driven session work and Loop runs.

### Risks

- A live Loop definition may change after selection. Revalidate its identity, version, inputs, prerequisites, and permissions at admission; never auto-start a replacement.

## Implementation Notes

The UI may display defaults, but it cannot infer a hidden transition. Implementation and review Loops must be explicitly selected; no automatic commit, push, or publication follows a completed run.
