# ADR-005: Bind provider capabilities and worktree to each action

## Status

Accepted

## Date

2026-10-06

## Context

The current Spec worker reads one environment-wide provider and model. A task author must choose Codex or Claude, a model, reasoning effort, and checkout/worktree before each skill or Loop action. Later edits to connection labels, runtime configuration, or worktree state cannot rewrite past attempts or silently change an action already in progress.

## Decision

Persist a versioned proposed selection per task action. On each accepted start, atomically bind every declared runtime role's immutable connection identity, provider, model, and reasoning choice, plus the resolved checkout/worktree identity and Loop definition/version where applicable. Record the effective non-secret values and runtime pin on each attempt and expose them through review-package provenance. Revalidate each later action; fail closed if unavailable. Never choose a replacement account, model, reasoning level, or workspace implicitly.

## Alternatives Considered

### Read one global active provider at dispatch

- **Pros**: Minimal change to the worker.
- **Cons**: Cannot support per-action choice and can change a run's provider after admission.
- **Why rejected**: Contradicts task ownership and provenance requirements.

### Keep only a mutable selection with no attempt snapshot

- **Pros**: Smaller persistence change.
- **Cons**: Later rename, reconnect, or worktree removal would make historical execution ambiguous.
- **Why rejected**: Review packages need the actual effective execution identity.

## Consequences

### Positive

- Concurrent actions can use distinct supported providers and worktrees.
- History remains attributable after configuration changes.

### Negative

- Binding, concurrency checks, and migration of a populated database need careful implementation.

### Risks

- Auth material or a worktree may disappear after binding. Every new action must revalidate and show a recoverable blocked state while preserving approved content.

## Implementation Notes

Separate pre-start choice from the workflow row because that row is created only on first start today. Reuse the existing stage-start transaction and idempotency controls for binding, with one immutable snapshot per action/run. No automatic commit, push, merge, or user-owned worktree deletion follows from binding.
