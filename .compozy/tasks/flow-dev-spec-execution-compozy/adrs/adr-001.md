# ADR-001: Follow the approved planning route through Spec and Tasks

## Status

Accepted

## Date

2026-10-05

## Context

Flow Dev already retains a published Issue and an approved planning decision. The Dev Control `determine-spec-path` skill recommends `PRD` when product decisions remain, `TECH_SPEC` when product intent is settled but technical decisions remain, and `DIRECT` when specification is unnecessary. Authors can override the recommendation before approving planning.

The user requested buttons that follow this decision and explicitly postponed direct execution. During clarification, the user included task decomposition in the Spec delivery.

## Decision

Continue the same Flow Dev work item using its approved selected route. A `prd` selection exposes “Criar PRD”, followed by Tech Spec and Tasks. A `tech_spec` selection exposes “Criar Tech Spec”, followed by Tasks, without a mandatory PRD. Each next stage requires its own explicit start after the previous stage is approved. Approved planning remains unchanged.

Stop at an approved task package. Do not implement code or initiate implementation, review, QA, or PR creation. Retain `direct_execution` as a valid saved planning choice and explain that its continuation is outside this delivery; do not substitute a Spec route or expose an active execution button.

## Alternatives Considered

### Alternative 1: End after Tech Spec

- **Description**: Produce specification documents without decomposing work.
- **Pros**: Fewer product states.
- **Cons**: Leaves the requested preparation for implementation incomplete.
- **Why rejected**: The user explicitly included Tasks.

### Alternative 2: Launch the originally recommended route or the complete implementation pipeline

- **Description**: Derive the next action from the original recommendation, or automatically continue into code execution.
- **Pros**: Fewer clicks in the uninterrupted case.
- **Cons**: Can contradict the author's approved override and exceeds the requested scope.
- **Why rejected**: The approved selection owns progression, and direct execution and implementation were postponed.

## Consequences

### Positive

- Buttons represent the next eligible action for the actual approved decision.
- Both specification routes terminate in work prepared for later implementation.

### Negative

- The application must represent different stage sequences and a legitimate route with no available continuation yet.

### Risks

- A label supplied for the original recommendation could disagree with a human override. Derive available actions from the saved selected route and current stage eligibility.

## Implementation Notes

Transport and action representation belong to the TechSpec. The planning skill recommends a route; it does not generate arbitrary executable UI actions. Preserve the existing Issue identity, planning provenance, and authorization rules.
