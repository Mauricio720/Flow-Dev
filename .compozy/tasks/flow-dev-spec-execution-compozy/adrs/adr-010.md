# ADR-010: Build faithful stage-specific Human Views from a validated document model

## Status

Accepted

## Date

2026-10-05

## Context

The existing MarkdownPreview handles only basic paragraphs, lists and links. It cannot represent contracts, diagrams, story/test relations or a task graph. The product requires substantive review instead of a transcript or summary.

## Decision

Parse Markdown/GFM into a lossless source-linked document model on the backend. Each block records its source document, content hash and line/byte span. Validate a small generated package index against source bytes for story, test, ADR, task and decision relationships. The index supplements documents and cannot replace or contradict them.

Keep UI ownership inside `features/issues/issue-composer/spec/`. Provide stage-specific PRD, TechSpec and Tasks views with section navigation, full companion access, real version diffs, explicit decision blockers and planned-test labels. Unknown safe sections remain visible in full; unsupported material or inconsistent relationships produce blocking diagnostics rather than omission.

Render GFM tables and code as inert content, normalize scoped document links, and render supported Mermaid diagrams with strict settings and sanitized SVG in a sandboxed frame. Always provide the diagram source and a text explanation. Unsupported diagrams display a visible interpretation gap and require an agent adjustment before complete review. Never execute generated HTML or code.

Keep commands, state and pending questions prominent independently of paged history. Preserve pt-BR control copy and original document language, current design tokens, keyboard access, reduced motion, and reading position. Approval concerns the whole identified package; no fabricated per-section acknowledgement checklist is introduced.

## Alternatives Considered

### Alternative 1: Reuse the basic Markdown preview as the primary review surface

- **Description**: Reuse the basic Markdown preview as the primary review surface.
- **Pros**: Small implementation.
- **Cons**: Cannot expose the required structured relationships or faithful rich content.
- **Why rejected**: Does not meet Human View acceptance criteria.

### Alternative 2: Ask another model to summarize generated files into UI cards

- **Description**: Ask another model to summarize generated files into UI cards.
- **Pros**: Flexible summaries.
- **Cons**: May omit requirements or invent relationships and makes approval nondeterministic.
- **Why rejected**: Approval must preserve material source content.

## Consequences

### Positive

Gives humans navigable substantive content with traceable provenance and deterministic validation.

### Negative

Requires a parser, safe diagram rendering and maintained extraction/validation contracts.

### Risks

Parsing success alone cannot prove semantic completeness. Preserve all source blocks and expose unresolved scope/decision gaps explicitly.

## Implementation Notes

See the TechSpec for concrete interfaces, ownership, limits, recovery and verification gates. This ADR specifies the target implementation; it does not claim the integration is deployed.
