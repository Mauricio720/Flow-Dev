# ADR-002: Keep separate PRD and Tech Spec documents on Compozy 0.3

## Status

Accepted

## Date

2026-10-05

## Context

The source brief targets Compozy 0.3. The upstream `cy-create-spec` inspected on 2026-10-05 writes a unified `_spec.md` containing product and technical parts. The inspected `cy-create-tasks` consumes that unified document. These are source observations, not evidence that either workflow has run successfully through Flow Dev.

The user chose separate PRD and Tech Spec documents and explicitly confirmed that this must not mean using the deprecated runtime.

## Decision

Target Compozy 0.3 and retain separate product and technical artifacts. The PRD stage produces `_prd.md` and `_user_stories.md`; Tech Spec produces `_techspec.md` and `_tests.md`; Tasks produces `_tasks.md` and its individual task documents. Relevant ADRs remain associated with the same specification package.

Treat compatibility with the chosen Compozy 0.3 release as a required integration dependency. The downstream TechSpec must define and validate maintained skill adaptations or equivalent supported integration behavior for both document creation and task decomposition. Do not silently replace the documents with `_spec.md`, downgrade to 0.2, or claim legacy installed skills are already compatible.

## Alternatives Considered

### Alternative 1: Adopt the unified upstream Spec

- **Description**: Use the current `_spec.md` product/technical format directly.
- **Pros**: Matches the inspected upstream creation and task-decomposition contracts.
- **Cons**: Changes the artifact separation the user wants to inspect and approve.
- **Why rejected**: The user explicitly selected separate documents.

### Alternative 2: Use Compozy 0.2 for legacy workflow compatibility

- **Description**: Retain the deprecated runtime to match the existing local process skills.
- **Pros**: Resembles existing manually authored task directories.
- **Cons**: Violates the required runtime target and does not establish the interactive integration needed here.
- **Why rejected**: The user explicitly requires the current 0.3 line.

## Consequences

### Positive

- Product and technical decisions remain independently reviewable.
- The runtime target stays independent of the chosen document format.

### Negative

- The integration must maintain and verify compatibility beyond invoking the inspected upstream skills unchanged.

### Risks

- Beta releases and inconsistent extension naming in upstream material can invalidate assumptions. Validate a pinned release and its actual enrolled skill contracts before implementation depends on them.
- Task generation could accidentally require a PRD on the Tech Spec route. Its supported inputs must include the approved Issue and Tech Spec without fabricating a product document.

## Implementation Notes

This ADR selects product artifacts and a runtime boundary, not an adaptation mechanism. Runtime installation, state migration, compatibility experiments, and skill authoring are not performed by this PRD task.
