# ADR-007: Pin Compozy and maintain separate-document workflow contracts

## Status

Accepted

## Date

2026-10-05

## Context

The pinned 0.3.0-beta.29 create-spec writes _spec.md; create-tasks consumes it. PRD ADR-002 requires separate documents and prohibits the 0.2 fallback. The downloaded binary checksum and version were checked, but authenticated provider execution has not been demonstrated.

## Decision

Pin `v0.3.0-beta.29` and the release checksum, OpenAPI digest, provider version and managed skill bundle digest in server deployment metadata. Disable automatic runtime updates. Implement a narrow `SpecRuntimeGateway` for workspace/session creation, prompt submission, event replay, interactions and verified stop.

Maintain three Flow Dev skills (`flow-spec-prd`, `flow-spec-techspec`, `flow-spec-tasks`) as runtime resources under `packages/api/resources/spec/`. Their versioned contracts produce the separate PRD/story, TechSpec/test, and Tasks/task-file packages. Adapt templates and invocation behavior, not merely filenames. The TechSpec-only path consumes retained Issue/planning context without a PRD. The Tasks contract consumes the exact approved TechSpec/test package and applicable approved product input.

Use one runtime session per attempt. An adjustment or explicit retry creates a new attempt and session with preserved decisions, source revisions and request text. Browser reconnect and worker recovery reattach to the same attempt; they never create a new prompt. Permission grants do not carry across attempts.

Treat release/schema/skill/provider drift as `runtime_incompatible`; do not admit generation until capability checks pass. A real authenticated run for both routes, live questions, permissions, orphan recovery, replay and stop remains a mandatory integration gate. Binary startup and fixture tests do not satisfy it.

## Alternatives Considered

### Alternative 1: Invoke upstream skills unchanged

- **Description**: Invoke upstream skills unchanged.
- **Pros**: No maintained customization.
- **Cons**: Produces a unified spec and assumes that format for tasks.
- **Why rejected**: Violates the accepted artifact contracts.

### Alternative 2: Use legacy skills and runtime as installed

- **Description**: Use legacy skills and runtime as installed.
- **Pros**: Matches current manually created folders.
- **Cons**: Does not establish 0.3 behavior, isolation or live interaction support.
- **Why rejected**: Explicitly prohibited by the product decision.

## Consequences

### Positive

Isolates beta API drift and makes artifact compatibility executable.

### Negative

Flow Dev owns the adapted bundle and must rerun compatibility gates on every runtime, provider or bundle update.

### Risks

OpenAPI is not sufficient evidence for broker outcomes or provider behavior; preserve an evidence report and fail closed on unsupported interactions.

## Implementation Notes

See the TechSpec for concrete interfaces, ownership, limits, recovery and verification gates. This ADR specifies the target implementation; it does not claim the integration is deployed.
