# ADR-006: Run a dedicated Flow Dev worker with automatically provisioned isolated checkouts

## Status

Accepted

## Date

2026-10-05

## Context

The current two-slot tasks worker awaits bounded generate, publish and plan operations. Spec sessions may wait for a person indefinitely. No checkout or Compozy integration exists in the working tree. The user selected a persistent Flow Dev execution server, automatic checkout preparation, and an operator-managed agent account on 2026-10-05.

## Decision

Add `src/cli/specWorker.ts` inside `packages/api`, with its own admission pool and durable short reconciliation jobs. Flow Dev owns execution, checkouts, lifecycle and review; Dev Control continues its existing planning operation. Do not add a package or route Spec through Dev Control.

Provision a dedicated checkout for each work item using the bound stable GitHub repository identity and the author's refreshed repository authorization. Resolve the default branch once at the first start and retain its commit SHA for every stage/retry. Require a connected personal repository credential for Spec content and commands, including public repositories; this deliberately strengthens Spec access relative to the existing public-repository anonymous-read fallback without changing older flows.

Use an operator-configured provider/account/model on the execution server. Keep that credential independent of GitHub authorization. Run each attempt's Compozy daemon and provider in an isolated rootless OCI container, with a read-only repository snapshot and approved inputs, one writable current-stage document directory, and private runtime state. The supervisor holds GitHub and database credentials outside that container. No shared global Compozy installation or daemon state is migrated.

Use a persistent managed checkout as the canonical artifact destination and an isolated candidate workspace for each attempt. The supervisor alone promotes validated package files. The runtime cannot write Git metadata, source code, other packages or approved upstream documents.

## Alternatives Considered

### Alternative 1: Reuse the existing worker slots

- **Description**: Reuse the existing worker slots.
- **Pros**: Less orchestration code.
- **Cons**: A pending human interaction would consume capacity needed by publication and planning.
- **Why rejected**: Long-lived supervision has different lifecycle and admission semantics.

### Alternative 2: Dev Control executor or developer-local runners

- **Description**: Dev Control executor or developer-local runners.
- **Pros**: Reuses another agent service or developer machines.
- **Cons**: Adds an external delivery dependency or per-device connectivity and lifecycle.
- **Why rejected**: The user selected a Flow Dev worker on a persistent server.

## Consequences

### Positive

Provides one accountable execution owner and automatic project onboarding. Keeps repository tokens outside agent execution.

### Negative

Requires a Linux execution host, rootless container runtime, persistent volumes, provider provisioning and supervision separate from the web process.

### Risks

Container/provider compatibility and bounded egress must pass the real runtime gate. A prompt or Compozy permission mode alone is not an isolation boundary.

## Implementation Notes

See the TechSpec for concrete interfaces, ownership, limits, recovery and verification gates. This ADR specifies the target implementation; it does not claim the integration is deployed.
