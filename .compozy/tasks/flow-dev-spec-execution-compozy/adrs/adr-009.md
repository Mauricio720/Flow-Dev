# ADR-009: Capture immutable document packages with recoverable filesystem promotion

## Status

Accepted

## Date

2026-10-05

## Context

Approval must identify the exact reviewed bytes and companions. Filesystem changes and PostgreSQL transactions cannot commit atomically. Adjustments must preserve previous complete versions and approved upstream inputs.

## Decision

Capture source bytes, parsed Human View content, document hashes, manifest hash, producing attempt, upstream package IDs and validation diagnostics in PostgreSQL. Store UTF-8 documents in bounded text rows; do not introduce an object store for these bounded text packages.

Finalize through a durable journal: freeze candidate writes, validate and capture candidate bytes, record a prepared manifest, promote with compare-and-swap checks against the canonical checkout, then record installed/review-ready. Record each promotion step so crash recovery can finish or identify a mismatch without guessing. Approval additionally performs a worker-owned disk verification under the same package lock and commits against the exact current package/version.

Generate stable package slugs from the work-item UUID, never user-controlled titles. Reject traversal, symlinks, hardlinks and unexpected paths. Approved upstream files are read-only inputs. External drift blocks new generation and approval until the original bytes are restored or an explicit operator reconciliation preserves the external copy; no automatic overwrite or import-as-approved.

Keep complete packages, approvals, accepted answers and attempt history for the lifetime of the work item. Retain failed/canceled partial outputs as explicitly incomplete captured packages. Runtime diagnostic data may expire after thirty days once application capture is complete; runtime deletion never deletes application review history.

## Alternatives Considered

### Alternative 1: Read current checkout files on every review

- **Description**: Read current checkout files on every review.
- **Pros**: Minimal database storage.
- **Cons**: External edits silently change what approval means and files may disappear.
- **Why rejected**: Violates exact-version review and history.

### Alternative 2: Commit every generated revision into Git

- **Description**: Commit every generated revision into Git.
- **Pros**: Git provides history.
- **Cons**: Adds publication behavior, Git privileges and branch policy beyond the feature.
- **Why rejected**: The user chose local artifacts without automatic commits or push.

## Consequences

### Positive

Provides immutable review evidence and a recovery path across partial writes and storage failures.

### Negative

Requires explicit promotion journaling, storage limits and operator conflict recovery.

### Risks

Unexpected external writers cannot share an atomic transaction with the database; isolate the managed checkout, verify immediately before protected transitions, and stop on any observed drift.

See the TechSpec for concrete interfaces, ownership, limits, recovery and verification gates. This ADR specifies the target implementation; it does not claim the integration is deployed.
