# ADR-003: Review every stage through a Human View and request changes from the agent

## Status

Accepted

## Date

2026-10-05

## Context

Flow Dev's product value is making agent work understandable to a human. The user explicitly required this at every Spec stage, chose individual approvals, and chose requests to the agent as the correction mechanism.

## Decision

Provide a primary Human View for PRD, Tech Spec, and Tasks, covering their substantive contents, current state, pending decisions, and provenance. Markdown and technical traces are secondary inspection surfaces. A completion summary alone is insufficient for approval.

The author requests changes in the current stage, reviews the resulting saved revision, and approves that exact revision and its companion documents. Approval records identity and time and releases a separate start button for the next stage. Generation, adjustment, approval, and starting the next stage are distinct actions. Approving Tasks completes Spec preparation without starting implementation.

Keep approved stage versions as the inputs to later stages. A revision request does not rewrite an approved upstream decision. Product decisions that conflict with those inputs are surfaced explicitly instead of being silently reinterpreted.

## Alternatives Considered

### Alternative 1: Run all stages and review once at the end

- **Description**: Automatically pass generated outputs to subsequent stages.
- **Pros**: Requires fewer author actions.
- **Cons**: Propagates unreviewed decisions and hides where the author needs to intervene.
- **Why rejected**: The user chose approval at every stage.

### Alternative 2: Use raw documents as the primary review surface with a direct editor

- **Description**: Require document inspection and allow direct document edits in Flow Dev.
- **Pros**: Gives direct control of the underlying text.
- **Cons**: Weakens the requested Human View and introduces an editing capability the user did not select.
- **Why rejected**: The user chose agent-driven adjustments and emphasized human-oriented visualization.

## Consequences

### Positive

- The author can understand and correct decisions before they become downstream inputs.
- Review approval has an unambiguous document version and human owner.

### Negative

- Each artifact kind needs a suitable presentation; a generic transcript or Markdown panel is insufficient.
- More explicit stage transitions are required.

### Risks

- An abbreviated visualization could omit binding requirements. Make all material content, companion documents, and changes inspectable before approval.
- A background revision could make an approval stale. Require review of the current saved version and reject stale approval.

## Implementation Notes

The TechSpec defines artifact interpretation and presentation contracts. The product requires navigable sections and relationships, accessible controls, and no fabricated progress or unsupported conclusions.
