# ADR-005: Persist one deletion operation per immutable issue identity

## Status

Accepted

## Date

2026-10-13

## Context

GitHub deletion and local cleanup cannot share a transaction. A client, server, worker, or connector can stop after either side changes. Imported Ready issues may have no local task row. A task can also be publishing when deletion starts. The product requires truthful recovery and repeated requests that never select a different Issue.

## Decision

Store a deletion operation outside the task-owned table graph, uniquely keyed by the verified project, repository database ID, and Issue node ID for linked issues, or by task ID for unpublished issues. Freeze that identity before any stop or provider call. A transaction records the operation and fences issue admissions; a reconciler advances it through stopping, publication reconciliation, remote verification/deletion, and local cleanup. The provider call occurs outside the transaction. A remote result is recorded before local cleanup. Failed and uncertain operations retain the task and a safe reason. After cleanup, retain only a minimal completion receipt with IDs, outcome, and timestamps; it contains no issue title, body, conversation, path, token, or work history. Repeated calls return the existing operation's state.

## Alternatives Considered

### Alternative 1: Delete GitHub and local rows in one request without durable state

- **Description**: Call GitHub, then delete local rows, returning a single response.
- **Pros**: Fewer records and less orchestration.
- **Cons**: A timeout or restart cannot distinguish remote success from failure and can leave an orphaned issue or false success.
- **Why rejected**: It cannot satisfy recovery and in-flight publication requirements.

### Alternative 2: Retain the whole issue as a soft-delete tombstone

- **Description**: Hide the task while preserving all issue-owned content indefinitely.
- **Pros**: Simple referential integrity and audit history.
- **Cons**: Does not permanently remove the issue-owned Flow Dev history.
- **Why rejected**: The PRD requires permanent removal of that history after confirmed success.

## Consequences

### Positive

- A worker or request can resume after interruption from a persisted stage.
- Unclaimed Ready issues and claimed work items share one identity-bound operation.
- Completion receipts make stale requests idempotent without preserving issue content.

### Negative

- The database retains minimal identity metadata after deletion.
- Reconciliation and cleanup require explicit lease and fencing rules.

### Risks

- A late worker result could write after cleanup. Admission and settlement paths must check the deletion fence under the task lock.
- A publication in flight may have created an Issue. Its existing recovery mechanism must resolve it before the deletion operation chooses a remote target.

## Implementation Notes

Use the existing PostgreSQL transaction and lease patterns. Keep deletion operation rows outside task-owned cascades and never use the issue number alone as a lookup or mutation target.
