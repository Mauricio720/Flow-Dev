# ADR-002: Stop active issue work during deletion

## Status

Accepted

## Date

2026-10-13

## Context

An issue can be generating a draft, publishing to GitHub, planning, or running a later action when its deletion is requested. Waiting for the user to end every activity would prevent deletion at the moment they need it. Removing the record while work continues could produce new external changes or write results after deletion.

## Decision

Allow a deletion request in any issue state. Stop or cancel ongoing Flow Dev work for that issue and prevent new work from starting. Finish deletion only after the work is stopped and any in-flight GitHub publication is reconciled. Show deletion as in progress until the final outcome is known. If stopping or reconciling cannot be confirmed, keep the local issue and show a recoverable state; never report success while work can still recreate it.

## Alternatives Considered

### Alternative 1: Block deletion while work is active

- **Description**: Require the user to wait or stop each operation manually.
- **Pros**: Simpler operation ordering.
- **Cons**: Makes deletion unavailable for a common, important state.
- **Why rejected**: The user explicitly requested deletion while active.

### Alternative 2: Delete without stopping work

- **Description**: Remove records immediately and let workers finish.
- **Pros**: Faster apparent completion.
- **Cons**: Workers may still publish, execute, or save results after the issue disappears.
- **Why rejected**: The user chose to interrupt work before deletion.

## Consequences

### Positive

- Users can start deletion from any state without leaving background work behind.
- Completion means no active Flow Dev work remains for that issue.

### Negative

- Some deletions take time and need a visible progress state.
- A failed deletion can leave the issue present with its prior work stopped.

### Risks

- A provider request already accepted cannot be canceled locally; reconcile its result before deleting the GitHub Issue.
- Local or remote cancellation can be uncertain; do not discard the issue record until the outcome is known.

## Implementation Notes

The TechSpec must account for generation, publication, planning, and local execution independently and define recovery after process interruption.
