# ADR-006: Prove GitHub absence before local issue cleanup

## Status

Accepted

## Date

2026-10-13

## Context

GitHub can deny deletion, time out after accepting a mutation, or mask a moved or inaccessible Issue as missing. A successful mutation response and a missing GraphQL node have different evidentiary strength. The PRD forbids deleting the Flow Dev record while remote presence is unknown.

## Decision

Use the initiating person's current GitHub token. Before mutation, fetch the Issue by its stored node ID and verify its repository database ID, repository node ID, Issue number, Issue type, author ID, and `viewerCanDelete`; compare repository identity with the current project binding. Send GraphQL `deleteIssue` using the verified node ID only. After mutation, including after a timeout, verify absence with GitHub's REST Get an issue endpoint at the frozen repository and number. Treat `410 Gone` as confirmed deletion only after the caller's read access to that same repository is established. Treat `301`, `404`, authentication failures, GraphQL null, malformed responses, and provider outages as uncertain or blocked. If the Issue still resolves, retain the local record. A prior confirmed `410` may complete local cleanup on retry without another mutation. Every retry rechecks current local and GitHub authorization.

## Alternatives Considered

### Alternative 1: Treat any 404 or null GraphQL node as deletion

- **Description**: Infer absence from a failed read.
- **Pros**: Quick recovery after a timeout.
- **Cons**: A transferred or inaccessible Issue can also appear missing.
- **Why rejected**: It can erase the only local recovery record while the GitHub Issue survives.

### Alternative 2: Trust the mutation response alone

- **Description**: Clean up locally when `deleteIssue` returns without an error.
- **Pros**: One fewer provider read.
- **Cons**: It cannot resolve response loss or an invalid/incomplete provider response.
- **Why rejected**: The product requires confirmed remote absence, including after interruption.

## Consequences

### Positive

- Permission masking and repository transfers cannot produce a false local success.
- The same procedure handles an Issue deleted separately on GitHub.

### Negative

- Some valid deletions wait for a later read or an authorized person to recover access.
- A provider read follows the mutation, increasing latency and rate-limit use.

### Risks

- GitHub semantics may evolve; contract tests must pin the accepted `410` behavior and keep `404` conservative.
- Organization policy can still reject `deleteIssue` even when the UI showed it as available; preserve the local issue and report the denial.

## Implementation Notes

GitHub documents `deleteIssue(input: { issueId })`, `Issue.viewerCanDelete`, and REST Get an issue returning `410 Gone` for a deleted Issue in a repository the caller can read. The permission check is advisory; the mutation result remains authoritative.
