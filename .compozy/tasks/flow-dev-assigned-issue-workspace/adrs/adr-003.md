# ADR-003: Reuse task identity with verified source snapshots and reconciled claims

## Status

Accepted

## Date

2026-10-06

## Context

The existing task, planning, and spec stores retain publication history and approved packages. Downstream authorization uses `authorUserId`, and planning inputs require a successful `task_publication_attempts` row. These assumptions exclude externally created issues and conflate authorship with operation. A PostgreSQL transaction cannot atomically update a GitHub Project item.

## Decision

Keep `tasks.id` as the work identity. Add one issue-source binding per task and unique `(projectId, repositoryId, issueNodeId)` identity, immutable issue snapshots, and one claim record per source. Preserve actual publication receipts separately. Imports create an `imported` task with no Flow Dev author or fabricated publication attempt. Successful legacy publications backfill source bindings without assigning an operator.

Reserve a claim in PostgreSQL before sending its GitHub status mutation. Only read-back of the exact board item as `In Progress` completes a claim. Persist dispatch intent, a monotonically increasing fence, and uncertain results. Keep a pending reservation during ambiguous outcomes; never let another assignee overtake it. Release an unsuccessful reservation only after the dispatch is settled and a fresh provider read proves the item remains eligible in `Ready`. Keep its audit history. A failed request does not grant operator rights.

Use the claimed operator for downstream authorization and the initiating actor for worker repository access. Require fresh issue, board, assignment, repository, and project checks for new mutations. Retain authorship for authoring permissions and provenance. Remove the planning approval side effect that moves issues back to `Ready`.

## Alternatives Considered

### Alternative 1: Fabricate publication receipts for imported issues

- **Description**: Insert a successful publication attempt to satisfy existing planning joins.
- **Pros**: Fewer immediate changes to planning.
- **Cons**: Misrepresents who published the issue and corrupts recovery and audit semantics.
- **Why rejected**: A verified source snapshot is a distinct fact from publication.

### Alternative 2: Move the board first, then create ownership

- **Description**: Set `In Progress` before reserving a database record.
- **Pros**: Avoids a pending claim row before the provider call.
- **Cons**: Concurrent assignees can race; a crash loses the claimant identity.
- **Why rejected**: It cannot guarantee a durable first claimant or safe retries.

### Alternative 3: Build an independent work-item aggregate

- **Description**: Copy published tasks and their packages into a second workflow store.
- **Pros**: Separates authoring schemas completely.
- **Cons**: Duplicates identities, histories, controllers, and migration work.
- **Why rejected**: The existing task ID and downstream stores already supply the required history.

## Consequences

### Positive

- Imported and published issues share the same downstream journey.
- Concurrent claims resolve to one durable item and one completed operator.
- Source versions, authoring, and operator decisions remain distinct and auditable.

### Negative

- Publication-based planning joins, schema checks, worker guards, and DTOs must change together.
- Uncertain claims may remain blocked until GitHub or the user's authorization recovers.

### Risks

- GitHub offers no cross-system transaction or compare-and-set status mutation. Fresh checks, dispatch serialization, and read-back minimize races; later external changes block new actions.
- Legacy duplicate bindings must fail migration with a safe conflict report rather than choosing or deleting history.
- A permanently unavailable operator requires a future transfer policy; this feature preserves history and blocks reassignment.

## Implementation Notes

Backfill snapshots from exact retained publication content. Preserve old input hashes and use a versioned planning-source adapter for new operations. Retain deprecated publication foreign keys for historical operations. Stop or reconcile pre-cutover active workers before switching authorization.
