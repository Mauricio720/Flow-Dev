# ADR-001: Separate issue authoring from assigned issue work

## Status

Accepted

## Date

2026-10-06

## Context

The current task workspace combines Issue Author conversation, publication, planning, spec, and execution. This makes the chat difficult to use and ties post-publication work to the person who created the Flow Dev task. The team also needs to work on issues created directly in GitHub.

## Decision

Keep the Issue Author area focused on drafting, approval, and publication. Only Flow Dev administrators may create and publish issues there. Provide a separate assigned-issue workspace for every authorized user. It lists issues assigned to that user in the linked GitHub Project's `Ready` status, regardless of where they were created. Claiming an issue establishes one Flow Dev work item and one responsible operator, moves the board item to `In Progress`, and starts a distinct planning and execution journey. A published issue previously created in Flow Dev reuses its existing identity and history rather than creating a duplicate. The first eligible assignee to claim is the operator; other authorized members may follow progress without operating that work item.

## Alternatives Considered

### Alternative 1: Keep the entire journey in the authoring chat

- **Description**: Add assigned issues and execution controls to the existing chat.
- **Pros**: Reuses one screen and its navigation.
- **Cons**: Preserves the confusion the user wants to resolve and keeps authorship coupled to execution.
- **Why rejected**: It does not solve the primary product problem.

### Alternative 2: Accept only Flow Dev published issues

- **Description**: Work only on tasks that originated in Issue Author.
- **Pros**: Reuses the publication receipt as the sole entry point.
- **Cons**: Excludes eligible GitHub issues created elsewhere.
- **Why rejected**: The user explicitly chose any eligible assigned issue.

### Alternative 3: Permit every assignee to operate simultaneously

- **Description**: Multiple assignees share mutation controls for the same issue.
- **Pros**: Little coordination is required to start.
- **Cons**: Planning decisions, local execution, and approvals can conflict.
- **Why rejected**: The user chose first claim ownership with observation for others.

## Consequences

### Positive

- The authoring journey ends at publication, and assigned work has a clear entry point.
- External issues and Flow Dev issues share one downstream journey.
- One operator prevents concurrent, conflicting decisions for an issue.

### Negative

- Existing post-publication views and permissions need to be relocated and reconciled with operator ownership.
- The product must explain why an issue is unavailable when assignment, status, or access changes.

### Risks

- A claim may succeed while a GitHub status update fails or becomes uncertain. The product must show the partial outcome and prevent duplicate work items until reconciled.
- GitHub permissions or board configuration may prevent `In Progress`; the claim must not appear complete in that case.

## Implementation Notes

The technical specification must define a durable issue identity, an atomic claim rule, reconciliation for GitHub mutations, and migration of already published tasks. Existing authoring history remains readable.
