# ADR-004: Connect each developer machine through an outbound HTTPS companion

## Status

Accepted

## Date

2026-10-06

## Context

The current `LinkedLocalProject` inspects one server-side `SPEC_LOCAL_PROJECT_PATH`. Container execution cannot reach a developer's unrelated machine or assume its local services and browsers exist. The user selected option A: a Flow Dev local connector using outbound HTTPS, with no inbound ports on the developer machine.

## Decision

Implement the companion as a CLI entry in `packages/api/src/cli/localConnector.ts` and concern-owned application/infra modules in the existing API package. It pairs to the authenticated user's account using a short-lived, single-use pairing code approved in the hosted application. It polls the hosted command queue over HTTPS and journals accepted commands locally before dispatching to Compozy.

The companion registers user-approved Git roots locally and shares opaque checkout handles and safe readiness metadata. Absolute paths, environment values, provider credentials, raw logs, and browser traces stay on the machine. Commands identify a pinned link revision, source snapshot, action, run, and fence; no hosted command can select an arbitrary filesystem path. The operator's explicit start in the work area authorizes that specific checkout and action.

Run local actions through the compatible native Compozy runtime and local subprocesses. Extend the existing runtime launcher boundary to accept the actual workspace root rather than hard-coded `/workspace`. Reuse the existing bundled spec skills and action contracts; preserve project instructions and available project skills. Local provider logins and attempt grants stay local. Store only machine-scoped connection/model metadata in Flow Dev; host-wide provider credentials are not forwarded to machines.

Use server leases plus a local checkout lock and command journal to prevent duplicate effects across disconnects and restarts. A lost heartbeat marks the hosted run reconciling. Recovery inspects the original runtime identity; it never launches a new attempt automatically. Existing eligible hosted isolated/worktree choices remain available explicitly.

## Alternatives Considered

### Alternative 1: Reach a developer runtime through VPN

- **Description**: Hosted workers connect directly to private Compozy endpoints.
- **Pros**: Reuses direct runtime calls.
- **Cons**: Requires network setup and addressability for every machine.
- **Why rejected**: The user chose outbound HTTPS pairing.

### Alternative 2: Reach a developer runtime through a private tunnel

- **Description**: Tunnel a local Compozy endpoint to the host.
- **Pros**: Avoids a dedicated command queue.
- **Cons**: Adds tunnel management and exposes a broader control endpoint.
- **Why rejected**: The user chose a connector scoped to linked projects and accepted actions.

### Alternative 3: Upload the checkout and environment to hosted containers

- **Description**: Reconstruct the developer environment remotely.
- **Pros**: Centralizes execution infrastructure.
- **Cons**: Loses local services and dirty-state semantics and transfers environment secrets.
- **Why rejected**: It does not execute against the developer's actual environment.

## Consequences

### Positive

- Hosted Flow Dev works with user-owned checkouts behind NAT.
- Local browsers and services remain available to project gates.
- Credentials and raw local evidence stay on the machine.

### Negative

- Developers install and keep the companion running and authenticate their local runtime.
- The feature introduces pairing, polling, command journaling, and version compatibility checks.
- Native execution has the developer account's OS permissions; a Git root allowlist is not a complete process sandbox.

### Risks

- Compromised machine credentials can target that user's linked projects. Scope tokens to one machine/user, rotate them, support immediate revocation, and require fresh operation authorization.
- Missing native runtime capabilities block the affected action with a specific reason. Contract tests must prove local workspace, interaction, artifact capture, cancellation, and Playwright execution before release.
- Process escape is possible when trusted project commands run as the user. Enforce tool path restrictions and declared resource access; do not claim containment that the OS/runtime does not supply.

## Implementation Notes

Use HTTPS short polling instead of inbound listeners or a long-lived WebSocket requirement. Provide `pair`, `link`, `run`, `status`, and `unpair` CLI verbs. Persist pairing credentials and the private registry with restrictive filesystem permissions. An offline journal must preserve run identity and decisive results, not just buffered UI activity.
