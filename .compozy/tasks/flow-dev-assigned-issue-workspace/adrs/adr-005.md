# ADR-005: Require current structured gate evidence before gated success

## Status

Accepted

## Date

2026-10-06

## Context

Existing run settlement can infer success from runtime completion. That does not prove that project-required gates ran. Local files, environment variables, and browser artifacts can also carry information that existing key/regex redaction cannot reliably sanitize.

## Decision

Resolve applicable project instructions and referenced skills/gates in the local checkout before execution, using a read-only policy discovery step. Pin their content hashes and a structured gate manifest to the run. Use explicit project declarations and applicable instruction obligations; do not treat every package script as mandatory or invent Playwright requirements. An ambiguous or broken mandatory declaration blocks admission with `gate_policy_unresolved` or `instructions_invalid`.

Record each gate attempt with its command digest, execution identity, source/run revision, exit outcome, and one of `passed`, `failed`, `blocked`, `unrun`, or `unknown`. A gated action can succeed only after its current required gates passed and its runtime/artifact prerequisites succeeded. A gate-free action reports `none_required`, not a fabricated test pass. Use local Playwright's installed browsers, configuration, environment, and reachable services; classify setup unavailability separately from assertion failures.

Sanitize before connector egress. Share typed, bounded status and evidence records and inspected document artifacts. Keep raw terminal output, screenshots, traces, and private paths local. Redact known environment/credential values and absolute paths, reject unsafe artifacts, and fail closed when evidence cannot be sanitized. Shared views never serve a raw local payload as a fallback.

## Alternatives Considered

### Alternative 1: Treat agent completion as gate success

- **Description**: Trust a textual statement that checks passed.
- **Pros**: Requires no gate ledger.
- **Cons**: Allows failed, skipped, stale, or uncertain tests to appear successful.
- **Why rejected**: The PRD requires honest required-gate outcomes.

### Alternative 2: Always run a global Playwright command

- **Description**: Force browser tests for every action.
- **Pros**: Uniform execution path.
- **Cons**: Invents gates and ignores project-specific configuration and stage applicability.
- **Why rejected**: Project instructions define mandatory gates.

### Alternative 3: Upload raw browser and terminal artifacts

- **Description**: Redact only at display time on the host.
- **Pros**: Simplifies remote debugging.
- **Cons**: Secrets cross the trust boundary before sanitization and may survive in storage.
- **Why rejected**: Local private data must not enter shared history.

## Consequences

### Positive

- Completion status has auditable execution evidence.
- Playwright failures distinguish assertion errors from unavailable prerequisites.
- Authorized observers can inspect safe results without receiving local secrets.

### Negative

- Policy discovery, gate execution, and package capture require additional structured contracts.
- Some evidence remains available only on the developer machine.

### Risks

- Natural-language instructions cannot always be resolved deterministically. Use the existing agent for discovery, validate its manifest against cited local sources, and block unresolved obligations.
- A user-owned companion attests to execution; this is not hostile-client proof or remote hardware attestation.
- Changing instructions or checkout contents invalidates a prepared start rather than silently weakening gates.

## Implementation Notes

The manifest never overrides stricter applicable project rules. Required gates cannot be removed by browser input. Journal decisive outcomes before truncating logs. Bind gate results to the current run and final checked checkout state; earlier attempt results do not satisfy a later run.
