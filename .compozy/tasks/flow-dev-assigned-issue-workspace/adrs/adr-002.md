# ADR-002: Link each user's local project for project-defined execution

## Status

Accepted

## Date

2026-10-06

## Context

The present local-project option points to a path on the Flow Dev server. The requested experience works even when Flow Dev is hosted and each user has their project on a different machine. Project files may include uncommitted work, environment variables, skills, and gates. Browser execution is needed to satisfy a project's Playwright end-to-end gates.

## Decision

Allow each user to link their own local checkout to a Flow Dev project, including when the application is hosted elsewhere. Before an action uses that checkout, show the user the linked project and require an explicit start. The execution honors the project's own skills, instructions, and required gates. It can use locally available environment configuration and services needed by those gates, including Playwright browser tests. The user sees gate outcomes and relevant evidence. Environment values and other secrets never appear in shared task views or logs.

## Alternatives Considered

### Alternative 1: Use one checkout on the Flow Dev server

- **Description**: Administrators configure a shared server path for all users.
- **Pros**: Similar to the current server-path setting.
- **Cons**: Does not represent each developer's machine or local environment.
- **Why rejected**: The user selected a per-user machine link even for hosted Flow Dev.

### Alternative 2: Require every user to run Flow Dev locally

- **Description**: Application and checkout always run on one machine.
- **Pros**: Simplifies access to local files.
- **Cons**: Prevents the hosted application scenario the user selected.
- **Why rejected**: It narrows the required operating model.

### Alternative 3: Provide a generic browser automation feature

- **Description**: Offer browser control independently of project rules.
- **Pros**: A reusable manual testing surface.
- **Cons**: Adds a capability the user did not request and obscures project gate results.
- **Why rejected**: Browser use is specifically for project-defined Playwright E2E gates.

## Consequences

### Positive

- Executions can respect the user's actual project instructions and environment.
- Required Playwright E2E gates can run against the local application and services.
- Hosted Flow Dev remains useful with local developer machines.

### Negative

- The local machine must be reachable through an authorized execution mechanism, whose implementation belongs to the TechSpec.
- Machine availability and local dependency failures become visible execution states.

### Risks

- A local checkout can contain secrets and unrelated changes. Access must be scoped to the explicitly linked project and secret values excluded from shared output.
- A disconnected machine can interrupt a run. The work item must retain its last known state and permit an explicit recovery action.

## Implementation Notes

The technical specification must establish the trusted local execution mechanism, project identity validation, consent boundaries, safe log redaction, and recovery behavior. A server filesystem path alone cannot meet the hosted per-user requirement.
