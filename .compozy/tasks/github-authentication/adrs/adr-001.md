# ADR-001: GitHub identity and application session

## Status

Accepted

## Date

2026-09-30

## Context

Flow Dev has a GitHub login screen, but its button only navigates to the workspace. The workspace and project procedures currently accept visitors without a real session. The product serves developers who use GitHub, while repository connection and issue publication belong to separate features.

## Decision

Any GitHub account may authenticate and establish an application session. The application protects private screens and project data with that session, supports explicit sign-out, and asks the user to authenticate again when the session is no longer valid. Signing in does not grant access to repository content or permission to publish issues.

## Alternatives Considered

### Alternative 1: Require repository authorization during sign-in

- **Description**: Make repository selection and access a prerequisite for entering Flow Dev.
- **Pros**: A user could be ready for repository operations immediately after sign-in.
- **Cons**: Couples identity to project creation and asks for permissions before the user selects a project.
- **Why rejected**: Repository control belongs to the separate project-creation feature.

### Alternative 2: Restrict sign-in to an approved GitHub account list

- **Description**: Only listed accounts may create an application session.
- **Pros**: Limits who can reach the application.
- **Cons**: Requires account admission management now.
- **Why rejected**: The user explicitly deferred administrator control over which accounts may sign in.

## Consequences

### Positive

- The existing login screen becomes a real entry point.
- Identity and session access work independently of repository integration.
- Users can enter before receiving a project assignment.

### Negative

- A valid GitHub account can enter the application even when it has no project access.
- Repository operations remain unavailable until the project-creation feature provides that connection.

### Risks

- An authenticated but unassigned user could see project data if a route omits project authorization; all private project operations must enforce the project boundary.
- Revoked or expired authorization may interrupt a session; the user needs a clear reauthentication path.

## Implementation Notes

The TechSpec will choose the GitHub authorization mechanism, session handling, and protection points. No repository permission is required by this decision.
