# ADR-004: PostgreSQL, Better Auth e sessões revogáveis

## Status

Accepted

## Date

2026-09-30

## Context

O monorepo ainda não tem banco de dados nem autenticação. Identidades, sessões e permissões precisam sobreviver a reinícios e funcionar sob concorrência. O operador confirmou PostgreSQL como armazenamento disponível. O login deve pedir somente identidade GitHub, sem permissões de repositório. A sessão precisa ser revogável no servidor, e o backend deve verificar autorização em cada operação.

## Decision

Usar PostgreSQL com Drizzle ORM, migrações versionadas e o adaptador Drizzle do Better Auth. O Better Auth executa o fluxo OAuth GitHub e mantém sessões opacas no banco, com expiração após sete dias sem uso e exclusão no logout. Configurar `session.expiresIn: 604800`, `session.updateAge: 0` e renovação ativa: cada validação de sessão renova o prazo no banco, enquanto o navegador renova o cookie por uma chamada ao Route Handler do Better Auth. Não habilitar cache de sessão em cookie: a validação de cada operação protegida consulta a sessão persistida. Usar `auth.api.getSession({ headers })` no servidor, encaminhando somente `user.id` ao contexto tRPC. A sessão identifica o ator; papel de administrador e atribuições são consultados no PostgreSQL em cada operação. Um layout ou proxy pode redirecionar, mas a barreira obrigatória fica nos procedimentos tRPC, controllers e consultas autorizadas dos DAOs.

Configurar o provedor GitHub com `disableDefaultScope: true`, `scope: ["read:user"]` e `getUserInfo` personalizado que consulta apenas `GET /user`. Usar o ID numérico estável do GitHub como `account.accountId`. Como o modelo de usuário do Better Auth exige email, gerar `github-<id>@flowdev.invalid` somente como valor técnico. O aplicativo não o trata como endereço de contato nem o usa para autorização. Desabilitar associação implícita de contas por email. Better Auth pode persistir o token OAuth na conta; configurar `account.encryptOAuthTokens: true`, não o usar para repositórios e desabilitar endpoints de obtenção/renovação de token e vínculo de provedores que não fazem parte do produto.

O início social aceita parâmetros de escopo enviados pelo cliente. Um hook do servidor aceita apenas `provider: "github"`, rejeita `scopes` e `additionalParams` enviados pelo cliente e impede que uma chamada direta solicite `repo` ou `user:email`. Desabilitar fluxos de senha, cadastro e outros provedores. Ativar o limitador do Better Auth com armazenamento PostgreSQL para a rota de início social, a 10 pedidos por minuto por origem confiável. Fixar versões compatíveis e verificar opções e rotas efetivas durante a implementação.

## Alternatives Considered

### Alternative 1: Auth.js com adaptador Drizzle

- **Description**: Executar OAuth e sessões em banco pelo Auth.js.
- **Pros**: Integração conhecida com Next.js e sessões persistentes.
- **Cons**: O limitador distribuído e o bloqueio de superfícies de vínculo/token exigiriam composição adicional; o provedor GitHub padrão pede também `user:email`.
- **Why rejected**: Better Auth documenta o adaptador, sessões, limitação por banco e personalização do provedor necessários ao escopo escolhido.

### Alternative 2: JWT com permissões embutidas

- **Description**: Guardar identidade, papel e projetos num cookie assinado.
- **Pros**: Menos consultas ao banco.
- **Cons**: Revogação de sessão e mudanças de acesso dependeriam da expiração ou de uma lista de bloqueio.
- **Why rejected**: O PRD exige que alterações de atribuição e designação valham na próxima ação protegida.

### Alternative 3: OAuth e sessão feitos sob medida

- **Description**: Implementar estados OAuth, PKCE, CSRF, cookies e sessões no projeto.
- **Pros**: Controle total do fluxo.
- **Cons**: Mais superfície de segurança e manutenção para o mesmo comportamento.
- **Why rejected**: Better Auth fornece o fluxo GitHub e sessões persistentes compatíveis com Next.js.

### Alternative 4: SQLite local

- **Description**: Armazenar tudo num arquivo local.
- **Pros**: Operação local simples.
- **Cons**: Depende de disco persistente compartilhado ou de uma única instância.
- **Why rejected**: O operador escolheu PostgreSQL.

## Consequences

### Positive

- Logout e expiração invalidam sessões no servidor.
- IDs GitHub estáveis impedem transferência de acesso após troca de login ou email.
- Restrições únicas e transações resolvem cadastros e atribuições concorrentes.
- Rate limit e armazenamento da sessão funcionam entre instâncias que compartilham o banco.

### Negative

- A disponibilidade do banco passa a ser necessária em cada ação protegida.
- A renovação exata a cada uso escreve na tabela de sessões; medir carga e duração das validações em produção.
- O fluxo precisa personalizar o perfil GitHub e restringir os endpoints de autenticação expostos pelo Better Auth.
- O token OAuth persistido pelo adaptador precisa de criptografia, gestão do segredo e bloqueio de APIs de leitura de token.

### Risks

- Uma atualização do Better Auth pode mudar opções, rotas ou modelos; fixar versões e testar perfil sem email, escopo efetivo e endpoints bloqueados.
- A revogação da autorização no GitHub não informa imediatamente uma sessão local; a sessão expira normalmente e uma falha GitHub detectada numa nova autenticação não cria sessão. Não prometer revogação instantânea da sessão local.

## Implementation Notes

Criar uma GitHub OAuth App exclusiva para cada ambiente de desenvolvimento, staging e produção. Registrar em cada uma a URL pública daquele ambiente e o callback `${BETTER_AUTH_URL}/api/auth/callback/github`; configurar `BETTER_AUTH_URL` explicitamente, sem compartilhar Client ID, Client Secret ou `BETTER_AUTH_SECRET` entre ambientes. Os domínios concretos e os segredos são entradas da implantação. Guardar `BETTER_AUTH_SECRET`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` e `DATABASE_URL` apenas no ambiente do servidor. Cookies de sessão devem ser `HttpOnly`, `Secure` em HTTPS e `SameSite=Lax`. O Route Handler tRPC precisa repassar ao navegador o `Set-Cookie` de renovação; Server Components não renovam cookies por si. O token criptografado não é entregue ao navegador ou aos DTOs da API. Sanitizar destinos de retorno para caminhos internos. Verificar que `disabledPaths` bloqueia, no mínimo, `/link-social`, `/get-access-token`, `/refresh-token`, `/account-info` e autenticação por senha, sem bloquear `/sign-in/social`, callback, sessão ou logout. Validar `Origin` nas mutações de autenticação.
