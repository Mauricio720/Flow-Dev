# ADR-002: Project-scoped access with administrator assignments

## Status

Accepted

## Date

2026-09-30

## Context

Developers work within projects. The existing project catalog is public and has no user membership model. The user wants developers to choose from projects delimited by an application administrator, while repository ownership and connection are handled elsewhere.

## Decision

A signed-in non-administrator may see and select only projects assigned to their GitHub identity. One project is active at a time, and project operations are limited to that project. An administrator may view and use every existing project and can assign or remove project access for users who have signed in at least once. A user with no assignments may sign in but sees a no-project state and cannot access project data. Losing access to the active project ends access to that project and requires a new permitted selection, if one exists.

## Alternatives Considered

### Alternative 1: Let users select any existing project

- **Description**: A signed-in user sees the full project catalog.
- **Pros**: No assignment workflow is needed.
- **Cons**: Exposes projects beyond the administrator's intended boundary.
- **Why rejected**: The user requires the administrator to delimit visible projects.

### Alternative 2: Defer project isolation

- **Description**: Authenticate users now and add project permissions later.
- **Pros**: Smaller initial workflow.
- **Cons**: Leaves project data open to all authenticated accounts.
- **Why rejected**: The user chose project selection from administrator-assigned projects as part of complete authorization.

### Alternative 3: Require assignment before first sign-in

- **Description**: The administrator pre-registers a GitHub identity before it can enter.
- **Pros**: Avoids an unassigned account state.
- **Cons**: Blocks self-identification and requires account admission now.
- **Why rejected**: The user chose sign-in first and assignment afterward.

## Consequences

### Positive

- Project visibility and operations follow a clear, testable access rule.
- Administrators can manage access without creating projects or connecting repositories in this feature.
- An administrator can use any existing project without assigning themselves.

### Negative

- Newly signed-in users wait for an administrator to assign a project.
- The product needs a clear no-project state and an administrator view of users who have signed in.

### Risks

- Stale project selection after an assignment is removed could leak data; access must be checked against current assignments on every project operation.
- Existing public project procedures must be brought under the same authorization rule.

## Implementation Notes

The TechSpec will define durable identity and assignment storage, project selection, and authorization enforcement. This ADR does not define repository access or project creation.
