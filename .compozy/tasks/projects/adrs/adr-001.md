# ADR-001: One GitHub repository is the project source of truth

## Status

Accepted

## Date

2026-09-30

## Context

Flow Dev needs a project boundary before its workspace menus and a reliable source for future code-aware tasks and issues. The first idea allowed either a local folder or a GitHub repository. The user changed that direction during clarification and selected GitHub as the sole source of truth.

## Decision

Each Flow Dev project is linked to exactly one GitHub repository. A project cannot be created without a valid repository connection. The same GitHub repository cannot be linked to two Flow Dev projects. Repository rename or transfer preserves the project relationship when it is still the same repository; a different repository requires a new Flow Dev project. Local folder registration is outside this feature.

## Alternatives Considered

### Alternative 1: Choose either a local folder or GitHub

- **Description**: Let each project use one of two independent code sources.
- **Pros**: Supports code that has not been published to GitHub.
- **Cons**: Local paths depend on the Flow Dev host and cannot support GitHub issue publication without another relationship.
- **Why rejected**: The user chose GitHub as the sole source of truth.

### Alternative 2: Link a local folder and GitHub to one project

- **Description**: Keep a local checkout alongside its GitHub repository.
- **Pros**: Could read local unpushed changes.
- **Cons**: Creates two potentially conflicting versions of the code and complicates project identity.
- **Why rejected**: The user explicitly chose a single GitHub source and removed the local option.

### Alternative 3: Let administrators replace the repository

- **Description**: Keep the project and its history while changing its repository to a different codebase.
- **Pros**: A project can be reused without recreating it.
- **Cons**: Existing and future tasks, issues, and references could silently change meaning.
- **Why rejected**: The user chose a new project for a different repository.

## Consequences

### Positive

- Every project has a stable code context and an unambiguous GitHub destination for future issue work.
- Repository rename or transfer does not force users to recreate a project.
- The project catalog can display a meaningful repository identity and connection state.

### Negative

- Code that exists only on a local machine cannot be added as a project.
- The product depends on GitHub availability and repository authorization to read code.

### Risks

- A repository URL can change; the connection must follow repository identity and show a recoverable state if access is lost.
- Repeated project creation requests could create duplicates; the same repository must resolve to one project.

## Implementation Notes

The TechSpec will decide how to resolve stable repository identity, verify access, and respond to rename or transfer. This ADR does not prescribe a GitHub authorization mechanism.
