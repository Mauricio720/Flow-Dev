# ADR-002: Project membership and GitHub access both govern code use

## Status

Accepted

## Date

2026-09-30

## Context

The GitHub authentication PRD defines Flow Dev project assignments independently of GitHub repository permission. Project creation adds a live repository connection, including potentially private code. The user chose to require both permissions for code consultation.

## Decision

A non-administrator must have a current Flow Dev project assignment and access to that project's repository through their own GitHub identity to consult code or use repository-dependent actions. Administrators can see every Flow Dev project under the existing administrator rule, but also need GitHub access to consult its repository. Flow Dev membership alone never grants private GitHub code access. Users who can see a project but lack repository access see the project and a clear access state without code content. Repository access is checked again when it changes or expires.

## Alternatives Considered

### Alternative 1: Flow Dev assignment grants repository access

- **Description**: Read connected repositories using only the creator's or application's access and expose the result to assigned users.
- **Pros**: A project assignment is sufficient to start work.
- **Cons**: Could expose private code to someone who lacks GitHub permission.
- **Why rejected**: The user required both Flow Dev and GitHub access.

### Alternative 2: GitHub access alone grants project access

- **Description**: Show projects to everyone who can access their repositories on GitHub.
- **Pros**: No separate Flow Dev assignment is needed.
- **Cons**: Bypasses the administrator-managed project visibility decided in the authentication PRD.
- **Why rejected**: Flow Dev project assignments remain the application's access boundary.

## Consequences

### Positive

- Flow Dev never broadens a person's GitHub code access merely through project assignment.
- The relationship between application membership and repository permission remains understandable.

### Negative

- A user can see an assigned project but cannot use repository-dependent features until GitHub access is available.
- A project can temporarily become unusable when GitHub authorization is revoked or the repository is removed.

### Risks

- Cached or stale repository data could leak after access changes; repository-dependent content must follow current permission.
- GitHub organization restrictions can prevent access despite a valid sign-in; users need a precise recovery message.

## Implementation Notes

The TechSpec will determine the permission check and consent flow. Identity sign-in alone is insufficient for private repository access.
