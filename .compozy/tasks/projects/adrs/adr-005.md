# ADR-005: Persistir identidade imutável do repositório e migrar o catálogo legado

## Status

Accepted

## Date

2026-09-30

## Context

O protótipo guarda projetos em memória sem repositório. A especificação de autenticação prevê importar `flow-dev-demo` e outras entradas apenas com nome e descrição. O PRD deste recurso exige exatamente um repositório real por projeto, sem troca posterior, inclusive quando o repositório muda de nome ou proprietário.

## Decision

Adicionar a `projects` o ID numérico do repositório GitHub como texto decimal, `node_id`, proprietário e nome conhecidos, visibilidade, arquivo e versão de detalhes. Aplicar unicidade ao ID numérico, `node_id` e nome normalizado. O ID GitHub é imutável após a criação; nome e proprietário são apenas rótulos atualizados quando uma consulta autenticada confirma o mesmo ID. A migração requer um manifesto de associação `{externalKey, repositoryOwner, repositoryName}` para cada linha legada que será mantida; cada associação é verificada com uma conta administradora autorizada antes de gravar. Linhas sem associação verificada, incluindo `flow-dev-demo`, não entram no novo catálogo: o deploy aborta e exige corrigir ou remover explicitamente essas linhas. Após o backfill, adicionar `NOT NULL` e índices únicos. Não inventar um repositório de demonstração.

## Alternatives Considered

### Alternative 1: Usar URL ou `owner/name` como identidade

- **Description**: Guardar apenas o endereço atual do GitHub.
- **Pros**: Modelo simples e legível.
- **Cons**: Rename, transferência ou reutilização do nome podem ligar um projeto a outro código.
- **Why rejected**: A identidade deve acompanhar o repositório, não o caminho.

### Alternative 2: Manter projetos sem repositório como exceção permanente

- **Description**: Permitir `repository_id NULL` para registros importados.
- **Pros**: Preserva todas as linhas legadas sem intervenção.
- **Cons**: Viola a regra de exatamente um repositório e cria projetos cuja origem de código é ambígua.
- **Why rejected**: O PRD define uma única invariante para todos os projetos.

## Consequences

### Positive

- Rename e transferência preservam o projeto e seus futuros vínculos.
- Conflitos de criação são resolvidos por restrições únicas mesmo sob concorrência.
- O catálogo contém somente projetos com uma origem de código verificável.

### Negative

- A implantação exige um mapeamento operacional e falha se houver registro legado não resolvido.
- O rótulo salvo pode ficar antigo quando GitHub estiver indisponível.

### Risks

- A última URL conhecida pode apontar a outro repositório após exclusão e reutilização; toda resolução compara o ID retornado antes de usar conteúdo ou atualizar rótulos.
- A especificação de autenticação deve ajustar sua importação para exigir associação verificada quando este recurso entrar em produção.

## Implementation Notes

IDs GitHub são armazenados como texto decimal para evitar perda de precisão em JavaScript. O backfill e as restrições são migrações versionadas, transacionais onde possível; a verificação GitHub acontece antes da transação de escrita. Dados de demonstração da interface permanecem identificados como demonstração e não são apresentados como código do repositório.
