# ADR-006: Resolver estado de conexão por usuário e revalidar ações de repositório

## Status

Accepted

## Date

2026-09-30

## Context

Um projeto pode estar visível no Flow Dev mesmo quando um membro não tem permissão GitHub. O catálogo deve continuar rápido com muitos projetos, mas nenhuma indicação antiga pode autorizar leitura de código. GitHub pode responder 404 tanto para falta de acesso quanto para recurso ausente.

## Decision

Carregar a página do catálogo pelo PostgreSQL e mostrar imediatamente a identidade salva com estado `checking` ou `not_checked`. Uma consulta separada resolve, para os projetos da página, o estado por usuário: primeiro permissão Flow Dev, depois token OAuth pessoal e respostas GitHub; consultas GraphQL por `node_id` são agrupadas em lotes limitados. O estado de conexão não é uma concessão persistida. Toda futura operação de conteúdo ou escrita consulta novamente a permissão Flow Dev e GitHub com o token do usuário antes de devolver dados ou executar a ação. Um 404 ou `node:null` vira `unavailable_or_no_access` quando não há prova de exclusão. Um repositório público pode ser acessado pelo caminho público após validar que o ID retornado é o ID vinculado. O shell nunca confunde uma verificação pendente com conexão saudável.

## Alternatives Considered

### Alternative 1: Verificar todos os projetos antes de renderizar o catálogo

- **Description**: Bloquear o catálogo enquanto cada projeto consulta GitHub.
- **Pros**: Uma resposta já incluiria estados atualizados.
- **Cons**: Latência e rate limit crescem com o número de projetos; uma falha GitHub ocultaria o catálogo.
- **Why rejected**: O catálogo precisa permanecer navegável e sem truncamento.

### Alternative 2: Persistir uma flag global `connected`

- **Description**: Usar o último resultado de um administrador para todos os usuários.
- **Pros**: Consulta barata.
- **Cons**: Permissões pessoais diferem; a flag poderia sugerir acesso inexistente ou expor dados privados.
- **Why rejected**: O PRD exige acesso pela identidade atual.

## Consequences

### Positive

- Catálogo e projeto continuam identificáveis durante falhas GitHub.
- O estado e as ações refletem a autorização de cada pessoa.
- Consulta paginada evita chamadas GitHub para todos os projetos de uma vez.

### Negative

- O estado visual pode permanecer pendente por alguns instantes.
- Algumas falhas GitHub não permitem distinguir exclusão de falta de acesso.

### Risks

- Uma atualização tardia de outra seleção pode alterar a tela errada; o cliente descarta respostas cujo `projectId` já não é o atual.
- A revogação entre a checagem e uma leitura posterior exige nova verificação na própria operação e respostas privadas sem cache compartilhado.

## Implementation Notes

Os lotes de conexão têm limite de 50 IDs e cada resposta é indexada por `projectId`. Metadados confirmados atualizam proprietário, nome, visibilidade e arquivo somente quando o ID GitHub coincide; falhas não sobrescrevem a última identidade conhecida. Um estado pessoal jamais é persistido como estado global do projeto.
