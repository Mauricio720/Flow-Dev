# ADR-004: Autorizar repositórios com um segundo aplicativo OAuth GitHub

## Status

Accepted

## Date

2026-09-30

## Context

A especificação de autenticação limita o login de identidade ao escopo `read:user` e proíbe usar seu token para repositórios. Este recurso precisa consultar repositórios privados sob a permissão de cada pessoa. O usuário escolheu uma autorização OAuth separada com escopo `repo`, sem instalação de GitHub App.

## Decision

Registrar um segundo GitHub OAuth App por ambiente, exclusivo para acesso a repositórios. O usuário inicia um fluxo de código de autorização a partir de uma sessão Flow Dev válida; o callback valida `state`, troca o código no servidor, confere `GET /user` e só armazena o token se o ID GitHub coincidir com o ID da conta da sessão. O aplicativo de identidade Better Auth permanece com `read:user` e não recebe `repo`. Armazenar o token de repositório criptografado por usuário, fora dos DTOs e cookies. Pedir `repo` e, quando a configuração GitHub permitir tokens expirados, `offline_access`; tratar renovação e nova autorização como estados recuperáveis. Cada chamada privada usa o token do próprio usuário e verifica a autorização Flow Dev antes de chamar GitHub.

## Alternatives Considered

### Alternative 1: GitHub App com token de usuário

- **Description**: Instalar uma GitHub App nos repositórios e usar acesso na interseção entre instalação e usuário.
- **Pros**: Permissões mais finas e seleção explícita de repositórios.
- **Cons**: Exige instalação ou aprovação pelo proprietário de cada conta ou organização.
- **Why rejected**: O usuário escolheu a autorização OAuth separada.

### Alternative 2: Ampliar o OAuth usado para login

- **Description**: Acrescentar `repo` ao aplicativo Better Auth que identifica a pessoa.
- **Pros**: Um só consentimento e menos credenciais de implantação.
- **Cons**: Faz o login pedir acesso amplo a código e contraria a separação da especificação de autenticação.
- **Why rejected**: O acesso a repositórios deve ser opcional e independente do login.

## Consequences

### Positive

- O login continua possível sem consentimento para repositórios.
- A identidade do token de repositório é verificada antes de vinculá-lo à sessão Flow Dev.
- Revogação de acesso a código não elimina automaticamente a sessão de identidade.

### Negative

- O escopo OAuth `repo` é amplo e permite mais operações do que esta interface precisa.
- Cada ambiente requer duas configurações OAuth GitHub e mais um fluxo de callback.
- Um usuário pode precisar aprovar o aplicativo em organizações separadas.

### Risks

- Um token não pode ser compartilhado entre usuários nem enviado ao navegador; criptografia, logs redigidos e checagem de identidade reduzem o risco.
- A resposta 404 de GitHub pode significar ausência de acesso ou repositório removido; a interface não deve afirmar exclusão sem evidência independente.
- Tokens expirados ou revogados devem falhar de modo fechado e permitir nova autorização.

## Implementation Notes

O fluxo usa `state` vinculado à sessão e expirado, callback local fixo e uma chave de criptografia própria para tokens de repositório. O parâmetro `returnTo` aceita somente caminhos internos validados. O acesso de organização pode exigir aprovação adicional; o produto oferece orientação e nova tentativa.
